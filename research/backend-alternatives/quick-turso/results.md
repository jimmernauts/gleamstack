## Summary

As of **2026-08-22**, “Turso” names two materially different stacks. **libSQL Embedded Replicas** (`@libsql/client`) are the older, production-supported read-replica model: reads are local, but writes normally go to the Turso Cloud primary; `offline: true` is an exception with weaker/less reliable behavior. **Turso Sync** is the newer product/package (`@tursodatabase/sync`, browser package `@tursodatabase/sync-wasm`), launched **2025-10-08**. It uses the Turso Database engine (the Rust SQLite rewrite), local-first reads and writes, explicit `push()`/`pull()`, logical row mutations outbound, and a Turso Cloud remote source of truth.

It is technically close to Mealstack’s local-first requirement: a browser database can persist in OPFS, accept offline writes, and bootstrap/sync across devices. However, it is not a finished replacement for a strict product requirement. Sync is still Beta, Turso is pre-1.0, browser support requires OPFS plus COOP/COEP/SharedArrayBuffer and effectively one tab per database, iOS PWA compatibility is not first-party-established, default conflicts are last-push-wins, and user-owned Google Drive/S3/R2/Tigris backup is not native. Recommendation: **conditional/prototype tier, not the main shortlist** until iOS storage, delete/concurrency behavior, quota/eviction, and export/restore are proven in Mealstack.

## Key Findings

- **Browser/local storage:** `@tursodatabase/sync-wasm` uses a persistent OPFS file plus WAL/metadata; normal sync bootstraps the full database, satisfying “full dataset local” if the browser grants/retains quota. Partial sync exists but is experimental and unsuitable for this requirement. The browser implementation requires a Web Worker, synchronous OPFS, SharedArrayBuffer, and COEP/COOP; the same database cannot currently be opened in multiple tabs ([browser announcement, 2025-10-08](https://turso.tech/blog/introducing-turso-in-the-browser); [partial sync](https://docs.turso.tech/sync/partial)). Turso’s official iOS offering is a native Swift SDK using SQLite/libSQL, not Safari/PWA storage; no first-party iOS Safari compatibility guarantee was found ([mobile announcement](https://turso.tech/blog/turso-goes-mobile-with-official-ios-and-android-sdks)).
- **Offline and convergence:** Turso Sync writes locally while offline and retains changes until `push()`; first bootstrap normally needs remote reachability. Devices sync through Turso Cloud, not peer-to-peer. Remote changes are pulled as physical pages; the local copy eventually matches the remote. Same-row concurrent edits use **Last Push Wins** (push order, not local commit time); pull atomically rolls back to the synced state, applies remote changes, and replays unpushed local changes. A `transform` hook permits custom row-level merges, but there is no built-in CRDT. Exact concurrent-delete/tombstone semantics and user-visible ordering guarantees are not specified in the cited docs—treat them as unresolved, not inferred guarantees ([usage](https://docs.turso.tech/sync/usage); [conflicts](https://docs.turso.tech/sync/conflict-resolution); [launch, 2025-10-08](https://turso.tech/blog/introducing-databases-anywhere-with-turso-sync)).
- **Generation/stability:** Turso 0.7.0 was released **2026-07-13** and removed the engine’s beta warning, but explicitly remains pre-1.0; the JavaScript sync repository still says the package has not reached 1.0 and recommends independent backups. Sync/browser fixes and WASM tests are active. The sync repository is MIT licensed ([release](https://github.com/tursodatabase/turso/releases/tag/v0.7.0); [sync README](https://github.com/tursodatabase/turso/blob/main/bindings/javascript/sync/README.md)).
- **Cloudflare/self-hosting:** `@tursodatabase/serverless` is fetch-only and explicitly supports Cloudflare Workers, making the existing Worker suitable for remote SQL, token issuance, or backup orchestration—not for a durable file-backed browser replica. Local sync-server support is documented for development. BYOC/dedicated deployments are Enterprise offerings; Turso Cloud’s own durability uses AWS S3/S3 Express ([TypeScript reference](https://docs.turso.tech/sdk/ts/reference); [pricing](https://turso.tech/pricing); [durability](https://docs.turso.tech/cloud/durability)).
- **Pricing/backup:** The live pricing page lists Free, Developer ($4.99/month), Scaler ($24.92/month), and Pro ($416.58/month), with sync quotas of 3/10/24/100 GB respectively and metered excess. Turso’s `db export` produces a local SQLite snapshot (possibly not latest without sync); PITR restores a new Turso database. There is no documented native user-owned Google Drive or arbitrary S3-compatible backup workflow. Mealstack must add export/upload/download/restore, likely through the Worker; this is a substantive requirement gap ([export](https://docs.turso.tech/cli/db/export); [PITR](https://docs.turso.tech/features/point-in-time-recovery)).
- **Auth/security/migration:** Tokens can be database-, table/action-, read/write-, and time-scoped; JWKS lets Clerk/Auth0-issued JWTs authenticate during the Beta. A browser must receive a bearer token, so never ship an org/master token; use short-lived per-user scope or a per-user database. Flat recipe CRUD maps cleanly to async TypeScript SQL, but Mealstack still needs a bridge, sync loops/retry/UI invalidation, checkpointing (auto-checkpoint is disabled), token lifecycle, schema migration, conflict policy, and backup UX ([authorization](https://docs.turso.tech/sdk/authorization); [checkpoint](https://docs.turso.tech/sync/checkpoint)).
