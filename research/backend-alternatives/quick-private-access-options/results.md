## Summary

For this one-owner app, Cloudflare Access attached to the Worker is the calmest option: it keeps the current `workers.dev` deployment, requires no purchased domain or active zone, gates requests before the Worker runs, and is covered by Zero Trust’s free tier (listed for teams under 50 users). The Workers Free plan is a separate quota: notably 100,000 Worker requests/day and 10 ms CPU/invocation. [Cloudflare Access - Workers](https://developers.cloudflare.com/workers/configuration/cloudflare-access/) [Cloudflare Access pricing](https://www.cloudflare.com/sase/products/access/) [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)

Do not treat a Turso token as secret merely because Access or Tailscale gates the page. A browser doing direct sync must receive the bearer token and its owner can inspect it. Delivering a narrowly scoped, expiring token at runtime after Access is an improvement over embedding it in a public build artifact, but it remains exposed to every authorized browser. That is a recommendation/inference, not a documented Turso guarantee.

## Key Findings

- **Repository facts — `leopoldsw/cloudflare-auth`:** It is an independent, self-deployed auth kit: email/password, username login, magic links, verification/reset flows, D1-backed opaque cookie sessions, and Hono/plain-Worker adapters. Its documented deployment provisions one Worker, one D1 database, and `AUTH_SECRET`; it requires migrations and a public origin. Production email is a separate concern; terminal email is development-only. It explicitly excludes OAuth, passkeys, MFA, organizations, roles, and hosted auth. [README](https://github.com/leopoldsw/cloudflare-auth) [platform assumptions](https://github.com/leopoldsw/cloudflare-auth/blob/main/docs/platform-assumptions.md) [known limitations](https://github.com/leopoldsw/cloudflare-auth/blob/main/docs/known-limitations.md)
- **Repository maintenance facts:** GitHub shows no releases. The main branch’s latest feed entry is `chore(gates): enforce the one-command setup contract`, updated 2026-07-12; the preceding meaningful feature is the `cf-auth setup` production path. This is active but very new, with no release artifact. [Releases](https://github.com/leopoldsw/cloudflare-auth/releases) [main commit feed](https://github.com/leopoldsw/cloudflare-auth/commits/main.atom) Architectural recommendation: it is unnecessary dependency and attack/maintenance surface for a single Cloudflare-account owner; choose it only if the app needs application-local accounts rather than Cloudflare identity.
- **Cloudflare Access on `workers.dev`:** Worker-level Access is enabled in Workers & Pages → Worker → Access, then choose “All traffic” and an authentication policy. It automatically covers every domain associated with that Worker, including its `workers.dev` hostname and previews; alternatively, hostname-based Access can target exactly one `workers.dev` URL. The documented prerequisites are Zero Trust enabled and permission to manage Workers/Access—not a purchased custom domain or active zone. The Zero Trust team domain is a free account subdomain such as `<team>.cloudflareaccess.com`, not a purchased domain. [Workers Access](https://developers.cloudflare.com/workers/configuration/cloudflare-access/) [one-click Access](https://developers.cloudflare.com/changelog/post/2025-10-03-one-click-access-for-workers/) [Zero Trust FAQ](https://developers.cloudflare.com/cloudflare-one/faq/getting-started-faq/)
- **Free-plan distinction:** Cloudflare lists Access’s Free plan at $0 and “best for teams under 50 users” (the feature table lists a 50-user core limit), so one owner fits. This does not raise Workers quotas: Workers Free remains 100,000 requests/day, 10 ms CPU per invocation, 3 MB compressed Worker size, and 20,000 static files/version. [Access pricing](https://www.cloudflare.com/sase/products/access/) [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/) [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- **Tailscale:** Serve proxies a service running on a device to other devices/people in the tailnet; Funnel proxies a local service to the public Internet. Therefore Tailscale cannot retroactively privatize an already Cloudflare-hosted `workers.dev` Worker. Tailscale-only access requires moving the app to a tailnet device or putting a reverse proxy/host on one; the browser device must be a tailnet participant (or use documented device sharing). Serve may add documented user identity headers; Funnel does not. If using headers, the backend should listen only on localhost. Disable the Worker’s `workers.dev` route (`workers_dev=false`) and preview URLs separately, or the public path remains. [Serve](https://tailscale.com/docs/features/tailscale-serve) [Funnel](https://tailscale.com/docs/features/tailscale-funnel) [workers.dev](https://developers.cloudflare.com/workers/configuration/routing/workers-dev/)
- **Turso:** Official docs describe `@tursodatabase/sync-wasm` as the browser/WASM local-first-sync package and require an auth token for cloud sync. Turso tokens are JWTs that can be database/group scoped, read-only, table/action restricted, and expiring; token invalidation can rotate database/group signing keys, and the API documents token revocation. [SDK reference](https://docs.turso.tech/sdk/ts/reference) [authorization](https://docs.turso.tech/sdk/authorization) [token controls](https://docs.turso.tech/sdk/authorization/tokens) [revoke API](https://docs.turso.tech/api-reference/tokens/revoke)
- **Comparison/recommendation:** (1) **Access on workers.dev:** retains deployment, free, no code, identity gate — recommended. (2) **Worker-owned Basic Auth:** retains deployment and is free, but requires custom credential handling and has no Access IdP/session/policy features. (3) **cloudflare-auth:** capable local auth with D1, but disproportionate infrastructure and dependency surface here. (4) **Tailscale-only:** strongest private-network boundary, but requires a tailnet-hosted service/device and abandons the current Worker path. Use Access, disable any unintended public preview/path, and serve Turso credentials from a gated runtime endpoint using the narrowest practical scope and expiry. The last credential-delivery and build-cache observations are architectural recommendations/inferences, not Turso-documented behavior.
