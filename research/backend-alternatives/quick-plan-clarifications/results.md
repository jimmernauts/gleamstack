## Summary

Official Turso sources document sync primitives, not a browser-schema migration framework. `@tursodatabase/sync-wasm` exposes a local database plus explicit `connect()`, `pull()`, `push()`, and `sync()`; the current repository package is `0.8.0-pre.7`, while its package README is visibly stale/mismatched (it describes `@tursodatabase/database-wasm`). Treat repository source and the Vite example as authoritative, and pin/test the exact release.

Cloudflare Access can gate both the SPA and same-origin `/api/db-config`, but it authenticates the browser; it cannot make a Turso credential returned to that browser secret from that browser. Runtime delivery avoids build-time embedding, not client-side visibility.

## Key Findings

- **Migrations:** Turso documents Drizzle’s external `drizzle-kit generate`/`migrate` workflow and schema-database migration jobs (`GET /v1/jobs`, `GET /v1/jobs/:id`), but Multi-DB Schemas are marked **Deprecated** and concern parent/child cloud databases, not browser sync databases ([Drizzle](https://docs.turso.tech/sdk/ts/orm/drizzle), [schema jobs](https://docs.turso.tech/sdk/http/reference), [schema databases](https://docs.turso.tech/features/multi-db-schemas)). Embedded Replicas are a different model: writes go to the remote primary by default ([embedded replicas](https://docs.turso.tech/features/embedded-replicas/introduction)). No official `sync-wasm` migration API or SQL-migration-file runner was found. Turso explicitly says `user_version` is read-only on Cloud and recommends a `_schema_version` table ([limitations](https://docs.turso.tech/cloud/limitations)). **Recommendation:** app-owned ordered migrations, each in one local SQL transaction, tracked by `_schema_version`; this is application architecture, not a Turso requirement.

- **Browser sync:** The package exports `connect` and the source uses `authToken` (string or async function) as `Authorization: Bearer …`, `path`, `url`, optional `clientName`, and `longPollTimeoutMs` ([package](https://raw.githubusercontent.com/tursodatabase/turso/main/bindings/javascript/sync/packages/wasm/package.json), [source](https://raw.githubusercontent.com/tursodatabase/turso/main/bindings/javascript/sync/packages/wasm/promise-default.ts)). `connect()` initializes the worker/database; configured remote URLs bootstrap an empty database. Files are persisted through OPFS `navigator.storage.getDirectory()` and `FileSystemSyncAccessHandle` ([OPFS implementation](https://raw.githubusercontent.com/tursodatabase/turso/main/bindings/javascript/packages/wasm-common/index.ts)). `pull()` returns `true` iff changes were applied and `false` when empty; `push()` returns no documented change indicator. Offline writes remain local until push ([usage](https://docs.turso.tech/sync/usage)); conflicts are last-push-wins, with pull rollback/replay ([conflicts](https://docs.turso.tech/sync/conflict-resolution)). The official example requires COOP `same-origin` and COEP `require-corp` because of `SharedArrayBuffer` ([example](https://github.com/tursodatabase/turso/tree/main/examples/javascript/sync-wasm-vite)). Multi-tab sharing is still an open backlog feature ([issue #5679](https://github.com/tursodatabase/turso/issues/5679)).

- **UI staging:** Directly re-querying/updating each feature after its local SQL transaction is a reasonable local-first recommendation. Turso does not require a query-subscription registry, and reviewed sync-wasm sources document no local reactive query API. Add a centralized refresh/invalidation mechanism when `pull()` can return `true`; that is application architecture.

- **Access:** Access is an identity-aware proxy; self-hosted public-hostname applications and path-scoped application paths are policy-protected ([applications](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/), [policies](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/)). The origin/Worker receives `Cf-Access-Jwt-Assertion` (and browser requests commonly carry `CF_Authorization`); Workers must validate signature, issuer, and audience using the Access certs endpoint ([JWT validation](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/)). Therefore Access can protect `/api/db-config`; if that endpoint returns a Turso token, authenticated JavaScript can inspect it. Use calm wording: protected delivery, not a browser secret.

- **Plan correction:** Do local-only vertical slices first; run ordered local migrations before sync; establish the matching Turso schema later; then add bootstrap/auth, explicit push/pull, and refresh-on-`pull()===true`. A one-shot InstantDB export/transform/import is compatible with the unused-production/no-dual-write constraint and Turso’s SQLite migration/import direction ([migration](https://docs.turso.tech/cloud/migrate-to-turso)); no permitted official source documents an InstantDB-specific exporter, so the exact procedure remains uncertain. Last-push-wins is documented and acceptable for this single-user case.
