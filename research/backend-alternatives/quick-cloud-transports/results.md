## Summary

**Cutoff: 2026-08-22.** Both transports can carry a Mealstack protocol, but neither is a database-sync service. Keep Dexie/IndexedDB authoritative; upload deterministic, content-addressed operations and snapshots, then perform merge, tombstone retention, conflict resolution, and compaction in the application. **Confidence: high** for documented API behavior; **medium/low** where called out as an unknown.

**A — Google Drive is viable for low-frequency cross-device sync plus bootstrap/backup**, especially with a visible user-owned folder, but browser-only authorization makes unattended sync unreliable. **B — R2 is the cleaner immutable-log transport**: global strong read-after-write/list consistency, conditional object writes, and inexpensive requests. Tigris is comparable only after selecting a strong-consistency bucket location; it adds snapshot/object-version support but has a major lifecycle/CORS caveat.

## Key Findings

### A. Google Drive

- `appDataFolder` is hidden, app-only, non-shareable, and deleted when the user uninstalls the app or manually deletes its data folder ([appDataFolder](https://developers.google.com/drive/api/guides/appdata), last updated 2026-07-22). It is a good private sync namespace, not a dependable sole backup. A visible app-created folder/files under `drive.file` are user-visible and recoverable/shareable, but `drive.file` only grants files created by the app or opened/shared through Picker ([scopes](https://developers.google.com/drive/api/guides/api-specific-auth), 2026-07-22). Persist IDs; offer “reconnect folder” through Picker rather than assuming name search.
- GIS browser token mode returns short-lived access tokens; renewal calls `requestAccessToken()` and may require a user-driven gesture. It intentionally does not provide per-user refresh tokens. Long-lived refresh requires authorization-code flow and a backend storing refresh tokens ([token model](https://developers.google.com/identity/oauth2/web/guides/use-token-model)). Keep tokens memory-only; never ship Drive client secrets or refresh tokens in the PWA.
- Use one immutable blob file per op (`ops/<actor>/<opId>.json`), created with a pre-generated Drive ID so retrying an ambiguous upload yields `409` rather than a duplicate ([uploads](https://developers.google.com/drive/api/guides/manage-uploads)). `files.get?alt=media` downloads blobs; `files.list` discovers them. The changes feed is an efficient notification/index, not an op log: `changes.list` returns current file state/removals, supports `spaces=appDataFolder`, and uses non-expiring `nextPageToken`/`newStartPageToken` ([changes](https://developers.google.com/drive/api/guides/manage-changes); [REST](https://developers.google.com/drive/api/reference/rest/v3/changes/list)).
- Do not update one file as the authoritative append log: Drive supplies no application-level CAS/transaction/order guarantee. Keep snapshots as new immutable files, or update a manifest only as an advisory pointer. Revisions are not archival proof: non-head blob revisions are purgeable, typically after 30 days and earlier once 100 unkept revisions exist; at most 200 can be `keepForever` ([revisions](https://developers.google.com/drive/api/guides/manage-revisions), 2026-07-22).
- Quotas are ample for a single user but rate handling is mandatory: 1,000,000 units/minute/project, 325,000/user/project; list=100 units, download=200, update=50; use truncated exponential backoff for 403/429 ([limits](https://developers.google.com/drive/api/guides/limits), 2026-07-31). Permissions, storage exhaustion, domain policy, revoked consent, app uninstall, and user deletion are restore failures to surface—not sync conflicts.

**Sketch:** local op → enqueue → user-authorized upload → periodically list/consume changes → download unseen ops → deterministic merge → write a new snapshot and retain tombstones through the compaction cut-line. Bootstrap first downloads the newest visible snapshot, then all ops after its cut-line. **Pros:** familiar user backup, no server credentials, good recovery UX. **Cons:** consent interaction, quotas, mutable Drive metadata, hidden-folder deletion, revision retention, and no atomic manifest. Verdict: suitable for “sync when opened/explicitly authorized” and backup, not guaranteed background sync.

### B. Cloudflare R2 or Tigris

- R2 is strongly consistent for read-after-write, delete, metadata, and listing; same-key concurrent PUT/DELETE is last-completion-wins ([R2 consistency](https://developers.cloudflare.com/r2/reference/consistency/)). S3 `PutObject`, `HeadObject`, and `GetObject` support `If-Match`/`If-None-Match`; ETags and checksums are available (full-object CRC64NVME; composite CRC32/CRC32C/SHA-1/SHA-256) ([R2 S3 compatibility](https://developers.cloudflare.com/r2/api/s3/api/)). R2’s S3 `GetBucketVersioning`/`PutBucketVersioning` are currently unimplemented, so application-level immutable keys are required; lifecycle can expire/transition objects ([lifecycle](https://developers.cloudflare.com/r2/buckets/object-lifecycles/)).
- Tigris supports ETag preconditions and list-after-write, but consistency is location-dependent: Single-region and Multi-region are strong globally; Global and Dual-region can be eventually consistent cross-region ([consistency](https://www.tigrisdata.com/docs/concepts/consistency/); [conditionals](https://www.tigrisdata.com/docs/objects/conditionals/)). Snapshot-enabled Tigris buckets support a subset of object-version APIs and immutable bucket snapshots, unlike R2 ([snapshots/versioning](https://www.tigrisdata.com/docs/buckets/snapshots-and-forks/)). However, snapshot buckets cannot use lifecycle/TTL rules, and Tigris’s documented CORS configuration is for public buckets ([CORS](https://www.tigrisdata.com/docs/buckets/cors/)). **Unknown:** retrieved first-party docs do not establish Tigris checksum-algorithm parity with R2 or a native browser/private-bucket Worker binding; verify before selecting it.
- **Sketch:** `ops/<actor>/<opId>` immutable PUT with checksum and `If-None-Match:*`; packed immutable segments reduce LIST/PUT costs but require segment indexes and complete-download validation. `manifest.json` may use `If-Match` CAS; retry on 412. A Durable Object is optional: use one only when the design needs a globally ordered receipt sequence or serialized manifest updates; its single-threaded, strongly consistent storage provides that coordination ([DO](https://developers.cloudflare.com/durable-objects/concepts/what-are-durable-objects/)). Otherwise deterministic op IDs and merge make the manifest advisory.
- Browser safety: never expose R2/Tigris long-lived keys. Use an authenticated Worker/server to authorize prefix-scoped reads/writes, or short-lived presigned URLs. R2 URLs allow GET/HEAD/PUT/DELETE for 1 second–7 days and are bearer tokens ([R2 presigned](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)); Tigris permits presigned URLs up to 90 days and warns that same-key PUT overwrites ([Tigris presigned](https://www.tigrisdata.com/docs/objects/presigned/)). Configure exact-origin CORS and expose ETag/checksum headers.
- Current standard-tier economics: R2 $0.015/GB-month, $4.50/million Class A, $0.36/million Class B, free egress ([pricing](https://developers.cloudflare.com/r2/pricing/)); Tigris $0.02/GB-month, $0.005/1,000 Class A, $0.0005/1,000 Class B, free egress ([pricing](https://www.tigrisdata.com/pricing/)). Lifecycle must not delete ops/tombstones until every supported restore baseline has advanced.
