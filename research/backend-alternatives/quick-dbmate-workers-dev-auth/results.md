## Summary

**Review annotation — dbmate.** Current dbmate documentation describes a standalone CLI and Go library, plain SQL migrations, and filesystem SQLite. It does not document `libsql://`/`turso://` drivers, browser/WASM execution, or OPFS. Thus direct Turso Cloud and in-browser dbmate use are undocumented—not proven impossible, but unsuitable as plan assumptions.

**Review annotation — workers.dev.** Cloudflare documents free `workers.dev` hostnames and current Workers-specific Access protection for them. The proposed owner-auth alternative can instead use Cloudflare’s official Basic Auth Worker sample, removing Access/JWT validation and any custom-domain requirement, while retaining normal Free-plan limits and Basic Auth trade-offs.

## Key Findings

- **dbmate facts:** documented URL forms include `mysql://` (also MariaDB), `postgres://`/`postgresql://`, `sqlite:`/`sqlite3`, ClickHouse URLs, `bigquery://project/location/dataset`, and `spanner-postgres://`; `--driver` can override URL detection. Migration files are `[version]_[description].sql` with `-- migrate:up` and `-- migrate:down`; only the numeric version is recorded. (https://github.com/amacneil/dbmate/blob/main/README.md)
- Migrations run atomically by default; `transaction:false` disables that per block. Versions go in configurable `schema_migrations`, whose default schema is `version VARCHAR(255) PRIMARY KEY`. Relevant commands: `new`, `up`, `migrate`, `rollback`/`down`, `status`, `dump`, `load`, `wait`, `create`, `drop`. (https://github.com/amacneil/dbmate/blob/main/README.md)
- **Compatibility:** Turso documents `turso://` for Turso databases and `libsql://` for libSQL databases; neither is in dbmate’s documented protocol list. dbmate’s official entry points are CLI/Go, not browser/OPFS. Do not configure dbmate directly against Turso Cloud or claim it runs against OPFS. (https://docs.turso.tech/sdk/authentication; https://github.com/amacneil/dbmate/blob/main/README.md)
- **Recommendation:** keep dbmate files/version numbers canonical. Run dbmate `up`/`migrate` against each ordinary local `sqlite:` file. For OPFS, an app-owned adapter should extract the same `migrate:up` SQL, apply it through sync-wasm, and maintain the same `schema_migrations` table. For Cloud, a host-side adapter or official `turso db shell`/`.read` workflow should apply the same SQL and version rows. Turso says to use a metadata table rather than `user_version` on Cloud. (https://docs.turso.tech/cli/db/shell; https://docs.turso.tech/sql-reference/cli/shell-commands; https://docs.turso.tech/cloud/limitations)
- **Uncertainty:** Turso’s sync docs document local `push()`/`pull()` but do not establish that OPFS schema DDL should be the cloud migration mechanism. Treat schema rollout as out-of-band and app-owned until verified. (https://docs.turso.tech/sync/usage)
- **Cloudflare facts:** accounts receive configurable `workers.dev` subdomains; Worker-level Access automatically covers a Worker’s `workers.dev` hostname, and hostname-based Access explicitly accepts a `workers.dev` hostname. The generic self-hosted-app page says “active domain,” so distinguish that setup from the current Workers integration. (https://developers.cloudflare.com/workers/configuration/routing/workers-dev/; https://developers.cloudflare.com/workers/configuration/cloudflare-access/; https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/)
- **Recommendation:** authenticate every request before routing API or assets; set `assets.run_worker_first: true`, then call `env.ASSETS.fetch(request)` only after auth. Store the password as a Worker secret. Cloudflare’s sample documents the browser challenge, `Authorization` header, and 401 `/logout` pattern, but labels itself non-production and requires HTTPS because Basic credentials are not encrypted. Browser caching/logout behavior is user-agent-dependent; this is owner-only gatekeeping, not a hidden SPA session. (https://developers.cloudflare.com/workers/static-assets/routing/worker-script/; https://developers.cloudflare.com/workers/configuration/secrets/; https://developers.cloudflare.com/workers/examples/basic-auth/)
- `run_worker_first` causes matching asset requests to invoke the Worker; Free limits still apply, notably 100,000 requests/day and 10 ms CPU/request. Plan wording: “Use Worker Basic Auth on workers.dev; no custom domain, Cloudflare Access, or Access-JWT validation; normal Free limits and Basic Auth limitations remain.” (https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/; https://developers.cloudflare.com/workers/platform/limits/)
