## Summary

The requested `database-wasm-vite` example is **not Turso Sync**. It uses `@tursodatabase/database-wasm` and opens `local.db` with `connect()`; there is no URL, token, `push()`, `pull()`, bootstrap, or Turso Cloud dependency. A named database is persisted in browser **OPFS** (plus a WAL), while `:memory:` uses an in-memory backend. The inspected implementation contains no IndexedDB path. The example is therefore a real local browser database, not merely an in-memory demo, and local writes continue to work offline after the app assets are loaded.

Turso Sync is a separate API/package. The Sync docs use `@tursodatabase/sync`, require a local path, Turso Cloud URL, and auth token, automatically bootstrap an empty local database on first connect by default, and expose explicit `push()`, `pull()`, `checkpoint()`, and `stats()`. The sibling browser example uses `@tursodatabase/sync-wasm`, not the package in the requested local-only example; it embeds the token in client JavaScript and continuously loops `pull()` and `push()`. Thus the official example resolves the “can Turso run persistently in a browser without a server?” concern, but not the Mealstack product concerns around cross-device authority, credentials, user-owned backup, iOS qualification, multi-tab coordination, maturity, or Gleam integration.

## Key Findings

- **Exact package/API:** [`index.html`](https://github.com/tursodatabase/turso/blob/main/examples/javascript/database-wasm-vite/index.html) imports `@tursodatabase/database-wasm/vite`, calls `connect("local.db", { timeout: 1000 })`, creates a guestbook table/index, and performs ordinary prepared-statement `run()`/`all()` operations. [`package.json`](https://github.com/tursodatabase/turso/blob/main/examples/javascript/database-wasm-vite/package.json) confirms `@tursodatabase/database-wasm`, not `@tursodatabase/sync-wasm`.
- **Persistence:** In [`promise-default.ts`](https://github.com/tursodatabase/turso/blob/main/bindings/javascript/packages/wasm/promise-default.ts), non-memory databases register the database and `-wal` in a worker. [`wasm-common/index.ts`](https://github.com/tursodatabase/turso/blob/main/bindings/javascript/packages/wasm-common/index.ts) implements OPFS `navigator.storage.getDirectory()`, `getFileHandle()`, and `createSyncAccessHandle()`. `:memory:` bypasses OPFS; no IndexedDB implementation appears in these code paths. The package tests reopen `local.db` and verify its schema, confirming persistence across connections.
- **Vite/worker/headers:** [`vite.config.ts`](https://github.com/tursodatabase/turso/blob/main/examples/javascript/database-wasm-vite/vite.config.ts), [`server.mjs`](https://github.com/tursodatabase/turso/blob/main/examples/javascript/database-wasm-vite/server.mjs), and [`vercel.json`](https://github.com/tursodatabase/turso/blob/main/examples/javascript/database-wasm-vite/vercel.json) all set `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp`. The package creates a module worker and shared WebAssembly memory in [`index-default.ts`](https://github.com/tursodatabase/turso/blob/main/bindings/javascript/packages/wasm/index-default.ts); this is required because the WASM uses `SharedArrayBuffer`. The example itself has one internal worker setup; it provides no cross-tab protocol or multi-tab test.
- **Sync difference:** The exact [Sync usage docs](https://docs.turso.tech/sync/usage) document `@tursodatabase/sync`, Turso Cloud, first-connect bootstrap, explicit sync calls, offline writes, and “last push wins”; pull rollback/replays unpushed local changes (see [conflict resolution](https://docs.turso.tech/sync/conflict-resolution)). The sibling [`sync-wasm-vite/index.html`](https://github.com/tursodatabase/turso/blob/main/examples/javascript/sync-wasm-vite/index.html) uses `@tursodatabase/sync-wasm`, a `sync-guestbook.db` path, `VITE_TURSO_*` URL/token, and loops `pull()`/`push()`. Its README explicitly warns that the token is bundled and public. Current Sync WASM source registers additional OPFS files (`-wal-revert`, `-info`, `-changes`) and uses localStorage for protocol side-state; it is still not IndexedDB. Notably, the docs show `bootstrapIfEmpty: false`, while the current Sync WASM [`types.ts`](https://github.com/tursodatabase/turso/blob/main/bindings/javascript/sync/packages/common/types.ts) does not declare that option and [`promise-default.ts`](https://github.com/tursodatabase/turso/blob/main/bindings/javascript/sync/packages/wasm/promise-default.ts) derives bootstrap from whether the URL is present/function-valued. This needs verification before relying on documented offline-first initial bootstrap semantics in browser WASM.
- **Mealstack reassessment:** Local authority and offline local CRUD are now demonstrated. Remaining gaps: no built-in cross-device sync in `database-wasm-vite`; Sync is last-push-wins rather than a Mealstack conflict/deletion model, and the reviewed sources do not specify tombstone/undo behavior. No Google Drive/S3/R2/Tigris export, bootstrap, or backup adapter is shown. Client-visible Turso tokens are unsafe for private per-user databases without an authorization design. The package README says it is pre-1.0 and recommends backups ([README](https://github.com/tursodatabase/turso/blob/main/bindings/javascript/packages/wasm/README.md)); the example has no tests. No iOS PWA compatibility claim or Gleam adapter is supplied, so both remain validation/integration work.
